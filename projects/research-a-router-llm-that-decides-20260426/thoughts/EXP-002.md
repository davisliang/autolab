## Experiment: BOLA-Router vs Static-Threshold Baseline Under Domain Shift

### Goal

Test whether a BOLA-inspired online-adaptive router can limit quality degradation to <3% within 50 queries after an abrupt domain shift, compared to a static-threshold router calibrated on the pre-shift domain.

### Setup

**Simulated routing environment.** We do not call real LLM APIs. Instead we use a precomputed quality lookup table that maps `(query_difficulty, model_tier) → quality_score`. This allows thousands of routing decisions per second and full reproducibility.

- **Query difficulty**: sampled from a domain-specific distribution. Each "domain" is a Beta distribution over [0, 1] with different α, β parameters.
- **Model tiers**: Haiku (cost=1, quality ceiling ~0.6), Sonnet (cost=5, quality ceiling ~0.85), Opus (cost=25, quality ceiling ~1.0). Quality = `ceiling × sigmoid(k × (tier_capacity - difficulty))` with noise ε~N(0, 0.02).
- **Domain shift**: at query 500, abruptly switch from Domain A (β(2,5), mostly easy) to Domain B (β(5,2), mostly hard).

### BOLA Router (treatment)

1. Maintain rolling QCBS (Quality-Cost Balance Score) over last W=50 queries.
2. Per query, solve: `t* = argmax_t [ V × quality_estimate(t) − cost(t) × qcbs_penalty ]`
3. `quality_estimate(t)` initialized from 100-query warm-up, then updated with exponential moving average (α=0.1) from judge samples (10% of queries get oracle quality feedback).
4. V (budget-quality tradeoff) swept over {1.0, 2.0, 5.0}; report best and mean across V.

### Static-Threshold Baseline (control)

- Calibrated on Domain A (first 400 queries): if estimated difficulty < 0.4 → Haiku; < 0.7 → Sonnet; else → Opus.
- Thresholds frozen at query 400; no online updates after shift.
- Same compute budget (trivial since both are routing-only, no model training).

### Protocol

1. **Warm-up** (queries 1–100): both routers observe oracle quality for all queries (burn-in).
2. **Pre-shift steady state** (queries 101–500): normal operation, judge samples at 10%.
3. **Domain shift** (query 501): switch difficulty distribution.
4. **Post-shift evaluation** (queries 501–1000): measure quality degradation relative to oracle router that knows Domain B parameters.

### Metrics

| Metric | Definition | HYP-003 threshold |
|--------|-----------|-------------------|
| `quality_degradation_post_shift` | `1 − (mean_quality_bola[501:550] / mean_quality_oracle[501:550])` | < 0.03 |
| `queries_to_recover` | First query q ≥ 501 s.t. rolling-50 quality ≥ 97% of oracle | ≤ 50 |
| `mean_cost_per_query` | Average cost across all 1000 queries | Report (lower is better) |
| `routing_decisions_per_sec` | Wall-clock throughput of router logic | Report (addresses CRIT-003 latency concern) |

### Oracle Router (reference, not a competitor)

Routes each query to the cheapest tier whose expected quality ≥ 0.9 × Opus quality for that difficulty. Provides the ceiling for quality comparisons.

### Seeds & Reproducibility

Seeds [42, 137, 2024] control: (a) difficulty sampling, (b) quality noise ε, (c) judge sampling mask. Report mean ± stddev across seeds.

### Addressing CRIT-003 Concerns

1. **"Trivial variable substitution"**: The experiment measures whether the transplant *actually works* under shift. Even if the mapping is obvious, empirical confirmation under realistic noise and partial observability (10% judge rate) is non-trivial.
2. **"Narrow prediction scope"**: We test abrupt shift only (as pre-registered). Gradual drift is future work.
3. **"Latency concern"**: We report `routing_decisions_per_sec` to confirm the BOLA optimization adds negligible overhead vs. static threshold lookup.

### Sanity Gate

Overfit-32: run 32 queries with full oracle feedback, confirm BOLA router achieves > 95% of oracle quality (trivial with full information). Train loss analog = `1 − quality_ratio`; must decrease ≥ 50% from random routing baseline.
