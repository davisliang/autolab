## Experiment: Conversation-Aware Router vs Per-Query Router

### Design rationale

HYP-006 claims that encoding dialogue complexity trajectory (drift + topic entropy over a sliding window) into the routing feature set reduces unnecessary Opus/Sonnet escalations by ≥20% on MT-Bench multi-turn conversations.

CRIT-005 raised valid concerns: (1) narrow benchmark, (2) small sample (n=80), (3) circular baseline dependency. This plan addresses each:

1. **Sample size**: We bootstrap at the conversation level (not turn level) to get proper confidence intervals despite n=80. We also report turn-level metrics for transparency.
2. **Circular baseline**: The per-query baseline is frozen before any conversation-aware training begins. Oracle labels are computed independently from cached LLM-judge scores.
3. **Narrow benchmark**: Acknowledged as limitation; the plan focuses on demonstrating the mechanism works on the canonical multi-turn benchmark before expanding.

### Oracle labeling strategy

Since we cannot call real LLMs in a local experiment, we simulate routing decisions:
- Use sentence-transformer embeddings to compute a synthetic "complexity score" per turn.
- Map complexity to tier labels via fixed thresholds calibrated on MT-Bench metadata.
- The key question is whether conversation-context features (trajectory drift, topic entropy) improve prediction of these labels over per-query features alone.

### Evaluation protocol

Primary metric: `unnecessary_escalation_reduction_ratio ≥ 0.20`
Guard metric: `mean_quality_delta ≥ -0.02` (quality must not degrade by more than 2%)
Statistical test: Bootstrap 95% CI on conversation-level resampling (1000 iterations)

### Sanity gate

Before main run, train on 32 randomly sampled turns for 60s and verify train loss drops ≥50%.

### Ablation trigger

If primary metric passes, auto-ablation removes conversation features (trajectory_drift, topic_entropy, turn_index, is_followup_flag) and re-evaluates to confirm the mechanism is load-bearing.
