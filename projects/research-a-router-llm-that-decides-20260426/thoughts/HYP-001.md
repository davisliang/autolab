## Motivation

Current router baselines overwhelmingly use token-length or regex patterns to proxy difficulty. This under-exploits freely available syntactic and semantic signals. A richer feature set should yield a more calibrated routing decision without requiring a large secondary LLM.

## Mechanism

1. Extract features from the raw query text:
   - `token_count` – simple length signal
   - `type_token_ratio` – lexical diversity as a proxy for vocabulary breadth
   - `avg_parse_depth` – estimated via a fast dependency parser (spaCy sm model)
   - `task_type` – one-hot from a 4-class fastText classifier (math/code/factual/creative)
2. Train a small gradient-boosted tree (LightGBM) on ~5 k labeled examples where the label is the cheapest model tier that produces an answer within 2% of GPT-4-level quality (measured by LLM-judge score).
3. At inference, classify query → tier in <5 ms.

## Baseline

Length-only heuristic: route to Haiku if tokens < 150, Sonnet if 150–600, Opus otherwise.

## Pre-registered prediction

`routing_accuracy ≥ 0.85` on the held-out test split.
Direction: **greater**.

## Falsification

If multi-signal accuracy ≤ length-only baseline (estimated ~0.70), the hypothesis is rejected.

## Open questions

- How sensitive is routing accuracy to parse-depth estimation quality?
- Does task-type label need to be accurate, or does noisy classification still help?
