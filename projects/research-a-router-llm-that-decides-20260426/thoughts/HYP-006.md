## Gap this fills

Every surveyed routing method—FrugalGPT (LIT-005/LIT-006), RouteLLM (LIT-008/LIT-009), Hybrid LLM (LIT-007/LIT-019), AutoMix (LIT-020), RouterBench (LIT-021), and all four existing hypotheses (HYP-001 through HYP-004)—treats each query as an independent routing unit. Multi-turn conversations are nowhere in the LitFinding set. This is a systematic blind spot:

- A short follow-up query ("What does that imply for edge cases?") scores as *easy* on any per-query signal (low token count, low parse depth), but is actually semantically dense given the prior turns.
- Conversely, an isolated domain-switching query ("Now, write me a limerick about photosynthesis") looks syntactically complex but is trivially answered by Haiku.
- Per-query routers cannot see either pattern; conversation-aware routing can.

MT-Bench is the dominant multi-turn benchmark and is used in no existing routing paper for evaluation.

## Mechanism

1. **Dialogue feature extraction** (at each turn `t`):
   - Embed the current query `q_t` and the prior k=5 turns using a lightweight sentence encoder (all-MiniLM-L6-v2, 384-dim).
   - Compute `trajectory_drift` = mean pairwise cosine distance across the k-turn embedding window.
   - Compute `topic_entropy` = entropy over the softmax of cosine similarities between each turn embedding and a fixed set of 8 topic prototype vectors (math, code, factual, creative, summarization, translation, reasoning, chitchat).
2. **Augmented feature vector**: Concatenate [HYP-001 query features] + [trajectory_drift, topic_entropy, turn_index, is_followup_flag].
3. **Router**: Same LightGBM classifier as HYP-001, retrained on MT-Bench training conversations with the augmented feature set. Label = cheapest tier that achieves quality within 2% of Opus on that specific turn.
4. **Unnecessary escalation metric**: Count turns where the router chose Sonnet or Opus but the per-query HYP-001 features alone would have sufficed (i.e., the simpler router also chose that tier) — compare to turns where the conversation-aware router correctly chose Haiku/Sonnet while the per-query router chose Sonnet/Opus.

## Experiment setup

- Dataset: MT-Bench 80 multi-turn question sets (8 turns each = 640 turn-level routing decisions).
- Train/test split: 60/20 conversations.
- Baseline: HYP-001 per-query LightGBM router applied turn-by-turn, ignoring history.
- Measure: unnecessary_escalation_reduction_ratio (turn-level) and mean quality (LLM-judge, Opus-only gold standard).

## Pre-registered prediction

`unnecessary_escalation_reduction_ratio ≥ 0.20` (≥20% fewer unnecessary Opus/Sonnet escalations vs. per-query baseline).  
Mean quality within 2% of per-query router.  
Direction: **greater**.

## Why this is novel

No routing paper applies conversation-level context as a routing signal. The dialogue trajectory drift metric is a direct analogue of concept drift detection in online learning (ADWIN, DDM) applied to conversational complexity — a cross-domain transplant from the continual learning literature. The proposed metric is also interpretable and cheap to compute (<1 ms).

## Risks

- MT-Bench has only 80 conversations; sample size limits statistical power. May need to bootstrap.
- all-MiniLM embedding adds ~15 ms per turn; must verify this is acceptable overhead.
- "Unnecessary escalation" operationalization depends on per-query baseline, creating circular dependency; must freeze baseline before evaluation.
