## Cross-Domain Transplant: Speculative Decoding → Speculative Model Execution

**Source domain**: Speculative decoding in LLM token generation (Leviathan et al. 2023, Chen et al. 2023). A fast draft model generates tokens speculatively; a verifier accepts or rejects each token, achieving the verifier's output distribution at the draft model's speed.

**Transplant insight**: Apply the same accept/reject logic at the *model* level rather than the *token* level. Run cheap Haiku eagerly to generate a full response. Use a lightweight judge to decide whether to accept it or escalate to Sonnet/Opus. Unlike input-feature routing (which routes *before* seeing any output), speculative execution routes *after* observing actual output quality signals—far more reliable for ambiguous queries.

**Why this is novel**: Prior routing work (RouteLLM, FrugalGPT, LLM-Blender) routes based on *input* features. Speculative model execution routes based on *output* quality, borrowing the accept/reject cascade from hardware-level speculation.

## Claim

On GSM8K (math reasoning, 1,319 test questions), a speculative execution router that:
1. Sends every query to Haiku
2. Passes Haiku's output to a lightweight judge (regex answer extraction + chain-of-thought length check)
3. Accepts Haiku's answer if judge approves; escalates to Sonnet otherwise

…achieves at least 8 percentage points more cost savings versus always-Sonnet, compared to a DistilBERT input-feature router (HYP-001 architecture), while keeping accuracy within 2pp of always-Sonnet.

## Prediction Rationale

- GSM8K has ~40% "easy" problems Haiku solves correctly
- Speculative router sees output quality directly; input-feature router guesses from query text alone
- Expected: speculative router correctly accepts ~35% of Haiku answers that input-feature router would unnecessarily escalate → 8pp cost saving improvement

## Experimental Design Notes

- Dataset: GSM8K test set (1,319 questions)
- Judge: regex extraction of final numerical answer; accept if answer is well-formed AND chain-of-thought length > 50 tokens
- Escalation: escalate to Sonnet if judge rejects
- Baseline 1: always Sonnet; Baseline 2: HYP-001 input-feature classifier
- Metric: cost savings in USD vs. always-Sonnet, normalized as percentage points
- Seeds: 3 judge threshold values × 3 API call orderings

## Open Questions

- What is the optimal judge architecture? Regex vs. embedding-based confidence vs. Haiku self-evaluation?
- Does escalation to Opus improve results for hardest problems?
- Is speculative execution latency-competitive given serial Haiku→Sonnet overhead?
