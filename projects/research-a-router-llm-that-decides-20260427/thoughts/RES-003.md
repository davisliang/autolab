## Result: EXP-003 — Batch Knapsack Routing FAILS Pre-Registered Threshold

### Sanity Gate

Spearman rank correlation between true and predicted H→S quality deltas on 32 examples: **ρ = 0.85** (threshold > 0.50). **PASS.**

### Verdict

**FAIL** — pre-registered threshold was ≥+20% cost reduction vs independent routing. Mean = **−16.75%** (batch costs ~17% MORE, not less).

### Root Cause Analysis

The greedy knapsack is outperformed by the independent threshold because of a structural flaw in the upgrade-candidate generation:

1. **H→S sweep exhausts budget first.** The algorithm sorts all 2N candidates by efficiency. H→S upgrades for moderate queries (pred_d ≈ 0.45) have high efficiency: eff = (P_S − P_H)/4 ≈ 0.139. With a budget of ~19K and only 4K needed to put all 1000 queries at Sonnet, the algorithm upgrades everyone to Sonnet.

2. **H→O candidates mispriced for S→O.** After all queries reach Sonnet, remaining budget is spent on H→O candidates sorted by (P_O − P_H)/24. But the actual marginal cost is now S→O = 20, and the correct efficiency metric is (P_O − P_S)/20. These rankings are reversed:
   - pred_d = 0.45: (P_O−P_H)/24 = 0.031 (ranked HIGH); (P_O−P_S)/20 = 0.009 (actually LOW)
   - pred_d = 0.65: (P_O−P_H)/24 = 0.026 (ranked low); (P_O−P_S)/20 = 0.021 (actually HIGHER)
   
3. **Result:** Moderate queries (already at P_S ≈ 0.78) get upgraded to Opus for +0.18 gain at cost 20. Hard queries (P_S ≈ 0.22 → P_O ≈ 0.65, +0.43 gain at cost 20) don't get upgraded. This wastes budget.

4. **Independent threshold advantage.** The optimal threshold t_s ≈ 0.30–0.38 naturally routes hard queries (pred_d > t_s) to Opus and moderate queries to Sonnet. This is a better partition: Opus is reserved for queries where Sonnet genuinely fails.

The batch router sends ~75% of queries to Opus (cost 25 each); the independent threshold sends only ~45–56% to Opus, compensating with more Sonnet calls (cost 5).

### Implication for HYP-008

HYP-008 posited that batch-level budget awareness would provide ≥20% cost advantage over per-query threshold routing. The experiment rejects this at the pre-registered threshold.

The underlying theoretical claim — that sorting by quality-gain-per-dollar provides better allocation than a fixed difficulty threshold — is sound in principle, but requires:
- Correct efficiency metrics for multi-step upgrades (S→O, not H→O applied post-H→S)
- Distinct query types where the batch-level view adds information beyond the local threshold signal

In this simulation with a steep quality model and moderate predictor noise (σ=0.12), the difficulty threshold already captures most of the routing signal. A corrected knapsack with proper S→O candidates would likely still not beat the threshold by 20%, given that both routers use identical noisy predictors.
