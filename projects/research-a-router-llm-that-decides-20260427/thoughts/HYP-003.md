## Cross-Domain Transplant: CPU Speculative Execution → Speculative LLM Routing

In modern CPUs, branch predictors guess the outcome of a branch and begin executing speculatively down the predicted path *before* the condition is evaluated. If the prediction is correct, no time is wasted. If wrong, execution is rolled back.

**The transplant**: In standard LLM routing, the flow is:
1. Compute routing decision (latency: R ms)
2. Call the selected model (latency: M ms)
Total: R + M

In speculative routing:
1. Fire Haiku call immediately (async)
2. Fire router computation in parallel (async)
3. Decision arrives: if "Haiku" → await Haiku result, return it (commit)
4. If "Sonnet" or "Opus" → discard Haiku call, fire the selected model
Total: max(R, M_haiku) + (M_selected if escalated else 0)

If the router is fast (e.g., a local embedding lookup) and Haiku is the right choice >50% of the time, speculative routing wins in latency.

## Why this is novel

Existing cascades (Matryoshka, FrugalGPT) are sequential: generate with small model → check quality → escalate. That adds the small model's latency on top of everything. Speculative routing eliminates the sequential router-then-call bottleneck by parallelizing the two operations.

## Mechanism

1. Router is a fast local model: sentence-transformer embedding + 3-class MLP, latency ~5ms.
2. Haiku call fired simultaneously (async HTTP).
3. If router says "Haiku": collect Haiku response, return.
4. If router says "Sonnet"/"Opus": cancel/ignore Haiku (note: incurs API cost for Haiku call even when discarded — this is the "branch misprediction penalty"), fire selected model.

## Cost Analysis

- When router is correct (say, P_correct = 0.7): total latency = max(5ms, T_haiku) ≈ T_haiku. Savings = T_router_sequential = ~5ms (small but adds up).
- Key gain: when query is sent to Haiku and Haiku IS the right call (50%+ of queries in typical workloads), latency = T_haiku (not T_router + T_haiku).
- Misprediction penalty: pay for wasted Haiku tokens on escalated queries. Budget impact: ~5% extra cost at 70% accuracy.

## Experimental Setup

- Simulate with async API calls, measure wall-clock latency distributions
- Baseline: sequential router → call (same router accuracy)
- Metric: latency_reduction_pct = (T_sequential - T_speculative) / T_sequential, at matched quality score
- Dataset: 1000 queries across MMLU/GSM8K/AlpacaEval
- Seeds: [42, 123, 456] (different query orderings)
- Expected: ≥15% latency reduction; break-even at Haiku selection rate ≥40%

## Open Questions

- Does the API provider support request cancellation? If not, the cost overhead of discarded Haiku calls may erode savings.
- What is the optimal router speed/accuracy trade-off for speculative routing? (Faster but less accurate router → more mispredictions → more cost waste)
