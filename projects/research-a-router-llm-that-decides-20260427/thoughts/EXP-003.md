## Experiment: Decompose-Then-Route vs Whole-Query Routing

### Goal

Test whether decomposing multi-hop questions into atomic sub-questions and routing each independently to the cheapest capable model reduces cost ≥15% at matched accuracy, compared to routing the whole query to a single (strongest) model.

### Dataset

**HotpotQA distractor dev set**, first 500 examples (deterministic ordering by original index). HotpotQA is structurally 2-hop: each question requires chaining two supporting facts. This makes it a clean testbed for decompose-then-route — each question decomposes into exactly 2 sub-questions with heterogeneous difficulty.

### Simulated Cost Model

Since we cannot call real Haiku/Sonnet/Opus APIs, we simulate the 3-tier model hierarchy with local models of increasing size:

| Tier   | Proxy Model                  | Simulated cost/token |
|--------|------------------------------|---------------------|
| Haiku  | Qwen2.5-0.5B-Instruct       | $0.25 / 1M tokens   |
| Sonnet | Qwen2.5-1.5B-Instruct       | $3.00 / 1M tokens   |
| Opus   | Qwen2.5-3B-Instruct         | $15.00 / 1M tokens  |

Cost = (input_tokens + output_tokens) × tier_rate for each call. Total cost sums all calls in the pipeline.

### Routing Mechanism

A lightweight BERT-based complexity classifier trained on a held-out HotpotQA split (200 examples, separate from the 500 eval set). The classifier outputs a complexity score ∈ {easy, medium, hard} per (sub-)question. Mapping:
- easy → Haiku (0.5B)
- medium → Sonnet (1.5B)  
- hard → Opus (3B)

Training signal: a question is "easy" if the 0.5B model answers it correctly (F1 ≥ 0.6), "medium" if 1.5B is needed, "hard" otherwise. This is pre-computed once and cached.

### Pipeline: Proposed (Decompose-Then-Route)

1. **Decompose** (Haiku-tier, 0.5B): few-shot prompt splits the HotpotQA question into 2 sub-questions.
2. **Route each sub-question**: BERT classifier assigns each sub-question to a tier.
3. **Answer each sub-question**: call the assigned tier model.
4. **Merge** (Haiku-tier, 0.5B): concatenate sub-answers, synthesize final answer.

Cost = decomposer + router (negligible BERT forward pass) + sub-question answers + merger.

### Pipeline: Baseline (Whole-Query-Route-All-Opus)

Route every question to the strongest model (3B "Opus" proxy). This is a conservative baseline representing the strategy "always pick the best model."

Cost = Opus-tier answer per question.

A second baseline variant uses the same BERT router on the whole query (without decomposition) for direct comparison of routing granularity.

### Metrics

1. **F1 accuracy**: token-level F1 between predicted and gold answer, averaged over the 500 examples (standard HotpotQA metric).
2. **Total simulated cost**: sum of all tier-rated token costs across 500 examples.
3. **cost_reduction_percent_at_matched_f1**: (baseline_cost - proposed_cost) / baseline_cost × 100, reported only when proposed F1 is within 1pp of baseline F1.

### Seeds

Seeds `[42, 123, 456]` control:
- Random ordering of evaluation examples (though we use fixed first-500, seeds control any stochastic decoding)
- Temperature=0.0 for deterministic generation; seeds affect any tie-breaking in the router training split
- Decomposition prompt sampling (nucleus sampling disabled; seeds control model init if applicable)

### Compute Budget

30 minutes total. Breakdown estimate:
- Router classifier training: ~3 min (small BERT on 200 examples)
- Baseline runs (3 seeds × 500 questions): ~10 min (single 3B forward pass per question)
- Proposed runs (3 seeds × 500 questions × ~4 calls each): ~15 min (most calls are 0.5B, cheap)
- Overhead (data loading, metric computation): ~2 min

### Addressing CRIT-007 Concerns

- **Overhead sensitivity**: we explicitly count decomposer + merger costs in the total. If decomposition overhead negates savings, the experiment honestly reports <15% reduction (hypothesis fails).
- **Scope**: we acknowledge HotpotQA is structurally 2-hop. Generalization claims are scoped accordingly.
- **Second baseline** (whole-query routing with same BERT router, no decomposition) isolates the effect of decomposition granularity from the routing algorithm itself.
