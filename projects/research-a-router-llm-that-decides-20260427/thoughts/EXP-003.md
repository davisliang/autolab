## Experiment: Portfolio Batch Routing vs Independent Threshold Routing (HYP-008)

### Motivation (cycle 2 — lessons from EXP-001 failure)

EXP-001 showed that structural overhead (always paying for cheap model + judge) killed the speculative cascade. HYP-008 avoids this pitfall: both batch and independent routers make the *same* routing decision (assign each query to Haiku/Sonnet/Opus) — the difference is *how* the assignment is optimized. Batch routing uses global budget awareness; independent routing uses per-query thresholds. No extra model calls, no structural overhead.

CRIT-014 argues the knapsack is standard and the contribution conflates quality prediction with budget allocation. This experiment isolates the batch-vs-independent comparison by giving **both strategies identical quality predictors** (same noisy difficulty estimates). The only variable is whether allocation is done globally (knapsack) or locally (threshold).

### Design

**Shared setup:**
- N=1000 queries per batch, 5 batches per seed, 3 seeds (15,000 total routing decisions per seed)
- Difficulty ~ Beta(2,3), mean ≈ 0.40
- 3 model tiers: Haiku (cost 1, ~40% acc), Sonnet (cost 5, ~72% acc), Opus (cost 25, ~88% acc)
- Quality: P(correct|d,m) = sigmoid(-(d - center_m) / 0.08)
- Both strategies see the same noisy difficulty estimates (σ=0.12)
- Quality tolerance: aggregate accuracy within 2pp of always-Opus

**Proposed (batch knapsack router):**
1. For each query, compute predicted quality deltas (Sonnet−Haiku, Opus−Haiku) and cost-effectiveness ratios
2. Build upgrade candidates sorted by cost-effectiveness (quality gain per dollar)
3. Greedily assign upgrades from Haiku baseline within total batch budget
4. Sweep budget parameter to find best cost at matched quality

**Baseline (independent threshold router):**
1. Route each query independently: if noisy_d < t_haiku → Haiku, elif noisy_d < t_sonnet → Sonnet, else → Opus
2. Sweep threshold pair (t_haiku, t_sonnet) to find best cost at matched quality
3. Same noisy difficulty estimates as batch router

### Key structural insight

The batch router's advantage comes from budget awareness: it can *redistribute* strong-model calls from low-delta queries near the threshold boundary to high-delta queries that the independent router might miss. This is especially valuable in the 3-tier setting where the cost ratio between tiers is large (1:5:25) — a single wasted Opus call buys 5 Sonnet calls or 25 Haiku calls.

### Primary metric

`cost_reduction_vs_independent_routing_pct`: (1 - batch_cost / independent_cost) × 100 at matched aggregate quality (within 2pp of always-Opus). Threshold: ≥20%.

### Sanity gate

Validates that the quality-delta predictor discriminates easy vs hard queries: Spearman rank correlation between predicted and true quality deltas on 32 examples must exceed 0.5.

### Seeds

[42, 123, 456] — 3 independent draws of difficulty, model outcomes, and predictor noise.

### Addressing CRIT-014 concerns

1. **Standard algorithm**: Yes, knapsack is standard. The test is whether batch-level optimization provides measurable advantage over per-query optimization in the LLM routing setting specifically. This is an empirical question, not an algorithmic one.
2. **Same quality predictor**: Both strategies use identical noisy difficulty estimates. The experiment isolates the allocation mechanism.
3. **3-tier setting**: The 1:5:25 cost ratio creates large asymmetry that batch optimization can exploit — a setting not tested in prior work.
4. **Aggregate vs per-query quality**: We enforce aggregate quality tolerance (matching HYP-008's claim), but also report per-batch breakdowns.
