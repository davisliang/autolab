## Gap Identification

Every router in the LitFinding set (all 25) treats the incoming query as an **atomic unit** and routes it to exactly one model. LLM-Blender (LIT-004) shows that no single model dominates even on a per-query basis — but no paper asks whether sub-parts of a single query could be routed differently. This is a striking absence: complex multi-hop questions (e.g., "Who directed the film featuring the actor who won the 1998 Oscar for Best Supporting Actor?") contain both easy sub-questions (factual recall: who won the Oscar?) and hard sub-questions (multi-step reasoning: chain to director). Routing the entire query to Opus because of the hard sub-part wastes cost on the easy sub-parts.

The **query decomposition** literature (Least-to-Most Prompting, Zhou et al. 2022; DSP, Khattab et al. 2022; DecomP, Khot et al. 2022) is entirely absent from the LitFinding set, even though it provides exactly the decomposition mechanism needed.

## Mechanism

1. **Decompose**: Use a lightweight decomposer (Haiku with a few-shot decomposition prompt) to split the incoming query into N atomic sub-questions.
2. **Route independently**: For each sub-question, apply an existing router (e.g., entropy-based HYP-001 or a simple BERT classifier) to select Haiku/Sonnet/Opus.
3. **Execute**: Call each selected model for its sub-question.
4. **Merge**: Concatenate sub-answers and use a lightweight synthesizer (Haiku) to produce the final answer.

## Why This Is Novel

- **Routing granularity**: all prior work routes at query granularity. This hypothesis introduces **sub-query routing granularity** as a first-class concept.
- **Complementary to existing routers**: the decomposition step is a pre-processing layer that any existing router can plug into. It does not require retraining the router.
- **Asymmetric complexity**: multi-hop queries have heterogeneous sub-question difficulty. A single-model route to Opus over-provisions on the easy hops.

## Cross-Domain Transplant

This hypothesis transplants **program decomposition** (structured program synthesis, module networks) and **divide-and-conquer query planning** from the question-answering / neuro-symbolic literature into the LLM routing setting. The analogy: complex query = compound program, sub-questions = subroutines, model routing = processor-level scheduling.

## Experiment Sketch

- **Dataset**: HotpotQA (multi-hop 2-hop questions) — inherently decomposable into 2 atomic sub-questions.
- **Baseline**: RouteLLM whole-query router (LIT-001 protocol) — routes entire HotpotQA question to one model.
- **Proposed**: Haiku-decompose into 2 sub-questions → route each via BERT entropy-classifier → merge with Haiku synthesizer.
- **Metrics**: (1) F1 accuracy on HotpotQA answers; (2) total token cost (input+output tokens × per-token price for Haiku/Sonnet/Opus); (3) cost-reduction% at matched F1.
- **Compute**: count decomposer + router + per-sub-question model + merger call costs in total budget.
- **Seeds**: 3 (random seed controls for sub-question ordering and decomposition prompt sampling).

## Pre-registered Prediction

Decompose-then-route reduces total inference cost by ≥15% compared to whole-query RouteLLM routing, measured on HotpotQA held-out split, at matched answer F1 (within 1pp tolerance).

## Risks

- **Decomposition overhead**: the Haiku decomposer adds latency and cost; if sub-questions are few (N=2), the overhead may negate savings. Mitigation: count decomposer cost in the budget.
- **Error propagation**: errors in sub-question answers compound in the merger. The F1 matching condition guards against quality degradation.
- **Decomposability assumption**: not all queries decompose cleanly. We scope to HotpotQA which is structurally multi-hop by construction.
