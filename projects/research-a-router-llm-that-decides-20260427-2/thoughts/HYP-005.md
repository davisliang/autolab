## Hypothesis HYP-005: Latency-Aware Routing

### The Gap

Every paper in the survey — FrugalGPT (LIT-001/005/008/019), RouteLLM (LIT-002/009/011), AutoMix (LIT-003/015/021), Hybrid LLM (LIT-006/013), RouterBench (LIT-014), LLM-Blender (LIT-010/012) — defines routing quality exclusively in terms of **token cost** (USD per query or tokens per query). Wall-clock latency — specifically time-to-first-token (TTFT), which is the dominant user-perceived delay in streaming LLM applications — is conspicuously absent from every objective function, every evaluation metric, and every baseline comparison.

This is not a minor omission. In production systems:
- Haiku TTFT ≈ 0.3–0.5 s
- Sonnet TTFT ≈ 0.8–1.5 s
- Opus TTFT ≈ 2.5–5 s

A cost-optimal router that routes 40% of queries to Opus to save money (by avoiding Sonnet "wasted" calls) may still be undeployable if those queries are latency-sensitive (e.g., interactive chat). No existing router reasons about this.

### Mechanism

Train a reward function:
```
R(query, model) = quality(query, model) - λ_cost · cost(model) - λ_lat · normalized_TTFT(model)
```
where λ_cost and λ_lat are Pareto-tunable trade-off weights. The router learns a 3-class policy (Haiku / Sonnet / Opus) using REINFORCE or PPO with this compound reward. At test time, a user specifies a cost budget; the λ weights are solved to hit that budget while minimizing latency penalty.

Baseline: same architecture trained with λ_lat = 0 (cost-only reward, matching FrugalGPT / RouteLLM objective).

### Why This Wasn't Done Before

Prior work treats routing as a pure cost-optimization problem. Latency profiles are not in RouterBench's cached-outcome format (it stores only correctness and model-choice cost). To run this hypothesis we augment the RouterBench splits with synthetic TTFT profiles drawn from published Anthropic API latency distributions, which avoids live inference cost.

### Predicted Outcome

Latency-adjusted quality (LAQ = MMLU accuracy / geometric_mean_TTFT_seconds, normalized to baseline) improves ≥15% at iso-cost compared to the cost-only baseline. This gap should be largest on latency-sensitive subsets (short factual queries where Opus adds latency but minimal quality gain).

### Pre-registered Prediction

- **Metric**: latency_adjusted_quality (LAQ)
- **Threshold**: ≥0.15 (15% relative improvement)
- **Direction**: greater
